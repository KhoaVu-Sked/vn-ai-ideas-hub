# Feature: Team view (replaces "Manager Dashboard") — ✅ Built (rebuilt this pass to follow a design mockup)

Part of [ai-learning-requirements](00-overview.md) — read that first for the status-tag legend and how these files relate.

Lives at `/learning-hub/team` (`features/learning/TeamPage.jsx`). Rebuilt to follow the same design mockup as the Learner Dashboard (`AI Learning dashboards.html`, repo root) — this time its **Team View** tab — rather than the plain stat-tiles-plus-roster layout described in earlier drafts of this doc. Same relationship as [04-learner-dashboard.md](04-learner-dashboard.md) has to that mockup's "My Progress" tab.

**Access — a real decision, not the original plan:** this app has no manager/report hierarchy anywhere (no `manager_id`, no "my direct reports" concept). Rather than build one, Team view reuses `accounts.role = 'admin'` — the exact same gate as Dashboard/Manage/Activity. That means **any admin sees every enrolled learner org-wide**, not a personal "my team" view scoped to specific reports. If a real hierarchy is ever wanted, that's new schema (an admin UI to assign who manages whom) — not built, not planned.

**Everything below is real, computed from existing tables — no new schema.** One addition is `getTeamOverview()` (`features/learning/queries.js`) now also returning a lean per-member `courses` array (`status`/`skills`/`quiz_total_questions`/`quiz_correct_first_try`) so `skillConfidence()`/`avgExamAccuracy()` (`features/learning/shared.js` — the exact functions the Learner Dashboard's own Retention card uses) can run client-side per member, rather than a second copy of that math in SQL. The other is a genuine cross-feature read: `getTeamIdeas()` (same file) reads the Ideas Hub's `ideas` table by owner and status only (`ideas.initiator_account_id`, `ideas.status`) — both already point at the same shared `accounts` table this feature's own `course_assignments` does, so this needed no new column, no new table, and no idea↔course link (see the Application card below for what that link would still be needed for).

**KPI row** — four tiles, matching the mockup:
- **Team completion** — a simple average of each member's own `core_complete`/`core_total` % (`pctOf`, the same function the roster rows and its sort already use) — every learner counts equally, regardless of how many core courses their own seniority level expects. (An earlier version pooled raw counts first — sum of everyone's `core_complete` over sum of everyone's `core_total` — which let whoever had the biggest course load dominate the number; that's arguably more representative of total work done, but didn't match what the roster's own % column visibly adds up to, which is what people actually check it against.) No "+X% MoM" trend, same reasoning as the Learner Dashboard's "Roadmap complete" KPI — no snapshot history exists, and a fabricated delta would be worse than none.
- **Active this week** — count of members whose `last_activity` (`course_assignments.updated_at`, most recent) falls within the last 7 days, out of the total. A plain rolling window (`withinDays`), not `weeklyStreak`'s own Mon–Sun boundary — there's no streak concept at the team level, just "who's touched anything recently."
- **Avg exam accuracy** — `avgExamAccuracy()` over every member's courses flattened into one list (a true team-wide average, not an average-of-per-member-averages). Named for what it measures — first-try correct-answers-over-total-questions — not a generic "score."
- **Ideas shipped** — count of ideas initiated by a currently-enrolled learner (`getTeamIdeas`) with `status = 'Launched'`, hint showing how many were submitted in total.

**Needs support card** (`needsSupportReason`, `TeamPage.jsx`) — the mockup's own version flags three categories (Stalled, Struggling, Stuck). **Stuck** stays out: it's Stalled again under a different name (same "hasn't touched it in weeks" signal, no separate data behind it). The other two are real, checked in this priority order (a person matching more than one is shown once, under the more urgent reason):
- **Stalled** — same signal as the roster's **Pace** column (see below).
- **Struggling** — this person's own average quiz accuracy (`avgExamAccuracy` — first-try correct answers over total questions, the same number the roster's "Avg Accuracy" column shows) is below **70%** (`STRUGGLING_ACCURACY_THRESHOLD`). This is the one hardcoded numeric threshold anywhere in this feature — set at the product owner's explicit request, not guessed at in code. Everywhere else, this app has no notion of a passing quiz score; the wrap-up quiz stays deliberately un-scored/un-gated ([03-your-journey.md](03-your-journey.md), 4.9). If this threshold ever needs to change, `STRUGGLING_ACCURACY_THRESHOLD` is the one place to edit it.
- **Behind** — same signal as Pace (below): this person's own % Complete is below the team's own real average, not a fixed invented target.

Each row is tagged with the same color pill the roster's Pace column would show for Stalled/Behind (a third color, reused from the Ideas Hub's own "Pilot" status, for Struggling). The "why" line is reason-specific: Stalled names the stale course, Struggling states the accuracy against the 70% mark, Behind compares % Complete against the team average. One row per flagged person, each with a working **"View roadmap"** button that opens the same drill-down a roster row does — not the mockup's decorative "Book a 1:1 · pair with buddy" button, which nothing in this app could actually do.

**Team progress table** — name, **Level → target** (e.g. "Junior → Middle"), enrolled track(s), % core-course complete + bar, in-progress count, **Pace**, **Avg Accuracy** (per-member `avgExamAccuracy()`), last activity (relative time), **Ideas** (how many Ideas Hub submissions this person has initiated, any status — a plain count off `getTeamIdeas()`, grouped client-side by `initiator_account_id` once for the whole table rather than filtered per row). Filterable by track, sortable by name or % complete — unchanged from before this pass. The track-combination breakdown that used to be its own "Learners" stat card (e.g. "3 on AI Track · 2 on AI Track + Core Competency") now lives in this table's own caption instead, so the KPI row could match the mockup's 4-tile set exactly.

**Pace** (`paceFor`, `TeamPage.jsx`) — three real states, in priority order: **Stalled** (same signal as Needs support above — takes priority, since going quiet entirely is more urgent than trailing the average); **Behind** (this person's own % Complete is below the team's own average — the same average the "Team completion" KPI shows, not a fixed invented target); **On track** (neither). No fabricated fixed pacing target anywhere — the comparison is always against the team's own real average, which moves as the team does.

**Skills across the team (heatmap) + Application/Distribution** — a two-column row, matching the mockup's own layout exactly: **Coverage** (the skills heatmap) runs the full height of the row on the left; the right column stacks **Application · AI Ideas Hub** above **Distribution**, not as a separate full-width section below both (an earlier pass got this wrong — Application sat full-width underneath the heatmap/Distribution row instead of stacked beside the heatmap).

**Skills across the team (heatmap)** — one row per skill (`courses.skills`, migration 028), one column per member, each cell bucketed into the mockup's 4-step scale (None/Learning/Proficient/Strong) off that member's own `skillConfidence()` percentage for that skill. "None" means no engaged courses for that skill yet, not a fabricated zero. Skills shown are whichever the team's own courses are actually tagged with — no hardcoded list — sorted by team-wide average confidence, strongest first. Cells and member columns stretch to fill the card's own width (`table-layout: fixed` + `<colgroup>`, only the skill-name column pinned to a fixed width) rather than sitting at a fixed pixel size regardless of how few members there are.

**Application · AI Ideas Hub card ("From learning to impact")**: real now — a funnel over every idea from a currently-enrolled learner, bucketed into the Ideas Hub's own real lifecycle (`STATUS_ORDER`, `features/ideas/constants.js`: Submitted → In Review → Approved → In Progress → Pilot → Launched) rather than the mockup's own Submitted/In progress/Shipped/Adopted labels — this app has no "Adopted" status, and forcing one in would be inventing vocabulary the Ideas Hub doesn't have. Each bar is a solid block (no background track behind it — an empty stage shows nothing, not a gray placeholder) colored by that status's own `STATUS_META` color, same palette the Ideas Hub's board uses. Below the funnel, in a boxed info panel matching the mockup's own callout treatment: a real substitute for its fabricated "62% of members who finished Applied have shipped..." conversion rate — **"{n} of {m} learners have submitted at least one idea"** — owner-only (`initiator_account_id` set-membership against the roster), no level/skill attribution needed. `On Hold`/`Declined` are excluded from the funnel, same as the Ideas Hub's own board treats them as off-timeline states. That panel doubles as an expand toggle ("Who's doing it ﹀") revealing a per-contributor breakdown (name, total submitted, shipped count) — collapsed by default so the card doesn't grow unbounded as submissions pile up.

**Distribution** — count of enrolled learners at each seniority level (`user_role.position`), as a bar chart scaled to the largest bucket. Every level gets a full-width, full-height track (the same "empty" color `ProgressBar` itself uses) with the actual count's fill bottom-anchored inside it, so a 0-count level still shows a same-size shape instead of a bare number floating over nothing.

That summary line doubles as an expand toggle ("Who's doing it ﹀") — collapsed by default, same reasoning as everywhere else on this card (don't grow unbounded as submissions pile up). Expanding reveals one row per contributor — name, total submitted, and shipped count if any — sorted by total submitted, most prolific first. No link out to a per-account idea list (none exists); this is a summary, not a new browse view.

**Drill-down** — clicking a roster row (or a "View roadmap" button on the Needs support card) opens that person's roadmap **read-only** — literally the same `JourneyTable` component the learner's own Journey page uses ([03-your-journey.md](03-your-journey.md), 4.4), given `readOnly` (disables drag-reorder) and `ownRoadmap={false}` (hides the Wrap-up link entirely, not just disables it — an admin can't jump into someone else's quiz from here). Scoped the same way the learner's own "My courses" is: `isExpectedByNow`/`effectivePosition` (shared.js) — courses at or below this person's own tier, plus one stage of early access once that tier's done — not every tier of the whole track. `GET /api/team/:accountId/journey` now also returns `position` (previously dropped) so the client can compute this the same way the Dashboard does for the caller's own view. Still just the roadmap table, not the full rich Learner Dashboard (KPI tiles, Confidence by skill, etc.) — reusing that whole page for an admin-viewing-someone-else context was considered and deliberately not built this pass; the drill-down's job is "check on this person's roadmap," not "see everything they'd see."

**Annual review date editor** — unchanged: in the Team progress card's header, next to the track/sort filters, a pill (`🗓 Annual review: Oct 13 ✎`) that expands into a native date picker on click. Saving PATCHes the same `app_settings.annual_review_date` row Auto Schedule's "Complete by" field defaults to ([07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md), 8.5/8.6) — the only cross-linked control in this app where an admin setting changes what every learner sees on their own page, live, with no redeploy.

**Deliberately not included:** the "Sync courses" / "Catalog last synced" control from early mockups — that's the Google Sheets pipeline in [01-course-catalog.md](01-course-catalog.md) (2.2), never built and not planned. No unmatched-skills review either, since the upload/matching flow it would review (old track-enrollment plan, [02-track-enrollment.md](02-track-enrollment.md)) doesn't exist. No per-member drill-down into the full Learner Dashboard (see above).

**Acceptance criteria:**
- [x] KPI row, Needs support, the roster table's new columns, the skills heatmap, and the distribution chart all show real, derived data — no fabricated numbers standing in for data that doesn't exist
- [x] "Needs support" shows Stalled, Struggling, and Behind — no invented Stuck category, and Struggling's 70% threshold came from the product owner, not guessed at in code
- [x] Pace's "Behind" compares against the team's own real average, not a fabricated fixed target; "Stalled" takes priority over "Behind" when both would apply
- [x] Skills heatmap and the roster's Avg Accuracy column use the exact same `skillConfidence()`/`avgExamAccuracy()` formulas the Learner Dashboard's own Retention card uses, not a second copy
- [x] Drill-down stays read-only: no reorder, no Wrap-up link into someone else's quiz
- [x] Drill-down shows only what's expected of this person by now (their own tier, plus early access), not every tier of the whole track
- [x] A learner with zero enrolled tracks doesn't appear on the roster; an admin with zero enrolled learners org-wide sees a plain empty state, never a broken page
- [x] Ideas shipped (KPI) and the Application card — real, scoped to currently-enrolled learners, derived from `ideas.initiator_account_id`/`ideas.status` only
- [ ] Per-idea skill/course attribution in the funnel (which skill each idea came from) — still blocked on an idea↔course link that doesn't exist anywhere in the schema
