# Feature: Your Journey (the learner's roadmap view)

Part of [ai-learning-requirements](00-overview.md) — read that first for the status-tag legend and how these files relate.

Lives at `/learning/journey`. Originally conceived as replacing a planned "Learner Dashboard" section — a real Learner Dashboard now exists too ([04-learner-dashboard.md](04-learner-dashboard.md)), at a separate URL, covering a different slice: this page is the roadmap itself (the **List** view only, as of this pass — see 4.4), the dashboard is progress-at-a-glance plus the **Mind map**, which used to live here.

### 4.1 Empty states — ✅ Built
- Zero enrolled tracks: "Nothing here yet — enroll in a track from the Learning Hub to start your journey," the hero shows only name + position (no track tags), progress shows **N/A** instead of a bar.
- Enrolled, but the selected track filter has no courses: "No courses in this track."

### 4.2 Hero — ✅ Built (replaced the earlier plain profile strip)
A dark navy band across the top of the page (`JourneyHero`/`JourneyPathRail`, `JourneyPage.jsx`) — avatar, name, a position badge (`user_role.position` — Intern/Junior/Mid level/Senior/Principal), and one tag: the currently-selected track (4.3 — there's no "All tracks" view any more, so this is always exactly one).
- A **Connect Google Calendar** pill sits in the top-right corner — "📅 Connect Google Calendar" (links to the existing `/api/calendar/connect`, same route Auto Schedule and the Get Started wizard use) or a quiet "✓ Google Calendar connected" once it is. This is the permanent home for "do it later" — the Get Started wizard's own Calendar step ([02-track-enrollment.md](02-track-enrollment.md)) is skippable, so declining it there isn't a dead end. `calendar_connected` rides along on the same `getJourney()` round trip as `position` (`features/learning/queries.js`).
- **The 5-stage seniority ladder (Intern → Principal)** renders as a connected path of circular nodes rather than a plain progress bar — every stage before the account's own position shows done (a checkmark), the current one shows a percentage ring, everything past it is dashed/locked. Once early access is earned (4.4) the +1 stage shows as a second, "bonus"-tinted node instead of staying locked. An account with no `position` assigned yet falls back to a plain bar — the rail has nothing to index into without one.
- Below the rail: **"N of M core courses complete (X of Y hrs)"** — `priority = 'core'` only, scoped to whatever the track dropdown currently shows, cumulative "through" the account's own officially-assigned position (never blended with early access — see 4.4). The hours figure sums each course's own `est_hours` across that same core-course set — a course *count* alone doesn't say much when a tier's courses range from 1 to 30 hours apiece ([01-course-catalog.md](01-course-catalog.md)).
- **Early-access selector** — once early access is earned (4.4), a segmented toggle appears next to the progress line (own local state, unrelated to the track filter in 4.3): "{my level}" (the same cumulative number above, unchanged) or "{next level} · bonus" (that tier's own core courses only, not accumulated with the tier below it — it's already done, since finishing it is what earned the early access, so folding it back in would just show ~100% again). Nothing appears here until early access is actually earned — there's nothing meaningful to switch to before then.

### 4.3 Track filter — ✅ Built (no "All tracks" — always exactly one track)
A pill-styled dropdown next to the "Your Journey" title: one option per enrolled track, no "All tracks" choice — there's always exactly one track selected. Filters the List view, the hero's own progress count, and Knowledge artifacts (4.8) — the whole page reads one track at a time (the Mind map has its own, independent copy of this same filter now — [04-learner-dashboard.md](04-learner-dashboard.md)). Auto-picks the first enrolled track on load, and re-picks whenever the current selection stops being valid (the selected track was un-enrolled out from under it — e.g. after a Reset).

### 4.4 Roadmap view — ✅ Built, List only
**List** (`JourneyTable`/`JourneyRow`, `JourneyPage.jsx`): a connected list of rows, not an HTML table — each course is a status-colored dot connected by a line to the next one, the same visual language as the hero's own tier rail (4.2) and Up next's mini path (4.7), so "Your Journey" reads as one continuous path from the hero band down into the list. **Core** courses come first, connected by that line; **optional** courses sit below a divider with no line running through them — they're enrichment, not part of what "core courses complete" counts, so they're set apart rather than mixed into the primary list. Priority no longer needs repeating on every row now that grouping already says it — a row instead shows the course title, its `focus_area` as a muted subtitle underneath (the actual competency a course builds — a branded title alone, e.g. "AI Fluency: Framework & Foundations," doesn't say what it's for), a single meta line (platform · hours · target date), and a status pill. Ordered Intern → Principal then by the roadmap's own authored sequence within a tier (see 4.6) — except that whatever's currently `in_progress` is pulled to the front of its own group first (4.6, 4.10). Scrollable after the list grows past a fixed height.

A row expands (click, or Enter/Space when keyboard-focused) to show the course link, its "after this course" outcome, and — first-person views only — **"Start this course"** and **"Take the quiz"/"Retake the quiz"** (4.10; both replaced a single Wrap-up link this section used to describe as gone — it's back, and no longer limited to one course at a time). A course with a scheduled session also shows **"Remove from calendar"** here — deletes just that course's own Auto-Scheduled event(s) and clears its target date, confirmed first (real calendar data, no undo); everything else about the course is untouched (07-scheduler-auto-schedule.md, 8.5). None of Start/quiz/unschedule render on Team view's read-only drill-down ([05-team-view.md](05-team-view.md)) — `JourneyTable`'s a shared component (also reused as-is on the Learner Dashboard's "My courses," [04-learner-dashboard.md](04-learner-dashboard.md), where Start/quiz DO render), but each action only shows up where a page actually passes its callback in.

**Scope — "your own tier only, plus early access":** the List only shows courses in the account's exact current tier (`isExpectedByNow`, `shared.js`, changed from an "at or below" cumulative comparison to a strict equality one) — an Intern sees the Intern tier, a Junior sees only the Junior tier, and so on. **The tiers below the account's own are assumed already fulfilled** (that's what earned the promotion into the current one), not something still owed — this replaced the earlier cumulative model, where a Junior saw Intern + Junior. Once every course in the account's own tier is `complete`/`skipped`, they automatically earn **one stage of early access** (`effectivePosition`, `shared.js`, capped "max +1 stage" — Intern → Junior, never Intern → Middle) — no action needed from the learner or an admin; it's a pure function of course status, re-derived on every load. The newly-visible tier's courses show up already unlocked, not "Locked." This is purely a *visibility* change — the account's own officially-assigned `user_role.position` never changes from it (still admin-only, see [08-data-model.md](08-data-model.md)); it only grows once an admin actually reassigns the position. The page's own subtext names this explicitly: *"Showing Junior — you've finished it and unlocked early access to Middle."* (`isVisibleNow`, `shared.js`, is the actual List/Mind-map-visibility helper — own tier OR the +1 early-access tier, deliberately not a cumulative range; `isExpectedByNow` alone, strict-equality, is what the % completion numbers and Team view's roster use.) The full roadmap (every tier, Intern through Principal) stays visible on the Mind map regardless (04-learner-dashboard.md) — that view is meant to show the road ahead; this one shows what's actually on your plate right now, plus whatever's just been earned.

**Milestone banners** — two, mutually exclusive (only the more-advanced one shows once both would apply), both a standing message re-derived from course status on every load, not a one-time dismissible toast (there's no "acknowledged" flag anywhere in this app's schema, and a condition already fully derivable from data doesn't need one):
- **Tier complete** (`tierJustFinished`): fires the moment the account's own official tier alone is fully done — the real annual-review milestone. Names the account's own `app_settings.annual_review_date` (the same date Auto Schedule's "Complete by" field defaults to — [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md)) and reassures on the one thing that could otherwise read as a gotcha: early access opens automatically, and it never touches this tier's own completion rate (which stays scoped to the raw position, per the hero above — that number doesn't move just because bonus material unlocked). Reads differently once there's no next tier to unlock (already at Principal): drops the early-access sentence, keeps the congratulations.
- **At ceiling** (`atCeiling`, pre-existing): fires once the +1 early-access tier is *also* fully done — nothing more unlocks automatically past that (the cap is flat, not recursive) until an admin reassigns the position. This supersedes "Tier complete" rather than stacking with it, since reaching it implies "Tier complete" already fired.

This page used to also render a **Mind map** as a second, toggleable view. That toggle is gone — the Mind map moved wholesale to the Learner Dashboard ([04-learner-dashboard.md](04-learner-dashboard.md)), and this page now shows the List unconditionally. A "See the Mind map →" link in the page's own subtext points there, so the option isn't just silently gone. `features/learning/JourneyTable`/`JourneyRow` (the List) and the Mind map's components (`MindMapNode`, `NodeRail`, `JourneyMindMap`) live in separate files — `JourneyPage.jsx` and `MindMap.jsx` — so both this page and the dashboard can use the List/Mind map independently without duplicating either. **`JourneyTable` is also reused as-is on the Learner Dashboard's "My courses"** (04-learner-dashboard.md) and on Team view's read-only drill-down ([05-team-view.md](05-team-view.md)) — it's the one shared list-row component for this whole feature, not three separate implementations.

### 4.5 Locking and Skip prerequisite — ❌ Removed (`fix-scoped-track`)
Both existed only to gate the old cumulative model (a Junior had to finish Intern's own courses before Junior-tier courses unlocked). Once tiers stopped being cumulative (4.4) — a role's own courses are workable regardless of the tier below it, since that tier is assumed already fulfilled — the gate had nothing left to check, so it and the escape hatch built for it were removed together, not left in as dead code:
- No course on the Mind map (or anywhere else) shows as **Locked** any more. `computeLocks` (`MindMap.jsx`) is gone; every node renders identically regardless of what tiers below it look like.
- **Skip prerequisite** (the button, `SkipConfirmModal`, `POST /api/courses/:id/skip`, and `skipPrerequisiteFor()` in `queries.js`) is gone — it only ever existed to satisfy the lock above, and there's no other reason to mark a whole tier below the current one `skipped` now that it isn't checked for anything.
- The `skipped` course status itself is **not** retired — a course can still be marked `skipped` (`STATUS_META`, `shared.js`), it's just that nothing in this app writes it any more today. Any historical `skipped` rows from before this change still display and count correctly (Up next/Auto Schedule's own-course eligibility, `isTierDone`, all still treat it as done).
- **Difference from the original plan:** the original Map view described per-course prerequisite arrows (course A requires specifically course B). That was never built — there's no `course_prerequisites` table — and the tier-gate that replaced it is now gone too, for the reason above.
- **Reset ("Reset everything")**: resets every table AI Learning itself owns for this account, not just course progress — clears all `course_assignments` rows (reverting everything to `not_started`, same as never having touched the journey), **and** `account_tracks` (un-enrolled from every track — this is what flips the Get Started gateway's own `onboarded` check back to false) and `calendar_connections` (Google Calendar disconnected). Deliberately does **not** touch `user_role` — that's general account data set on Manage → Users ([08-data-model.md](08-data-model.md)), not something this feature's own Reset control should be able to erase, even though tier-gating is its main reader; a learner whose seniority an admin already set keeps it across a reset, and can only get it changed the same way it was set. Added so the rest of the Get Started flow ([02-track-enrollment.md](02-track-enrollment.md)) can be re-tested from a fresh-enrollment state, not just the roadmap re-run with the same tracks/calendar still connected — after a successful reset the learner is sent to `/learning`, which shows the gateway again (the Role step stays skipped there if a position was already set). Also deletes any Auto Schedule events on the account's connected Google Calendar (best-effort, read BEFORE the reset since it's what deletes `calendar_connections` — see [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md), 8.5), so a demo account resets cleanly on both sides, not just this app's own data. (Reset itself is still a Your Journey control, not a Learner Dashboard one.) The button itself only opens a confirmation — a Skedulo-themed `ConfirmModal` (`features/learning/ConfirmModal.jsx`, red "danger" tone; shared with the Get Started wizard's own Calendar-skip warning, which uses the milder amber "caution" tone instead), not a native browser `confirm()` — the reset itself only runs from that dialog's own "Reset everything" click. **Staging-only**: the button (and its confirm modal) render only when `window.location.hostname` is `ts-ai-ideas-hub-staging.vercel.app` (`JourneyPage.jsx`'s own `isStagingHost` check) — the `/api/journey/reset` endpoint and `resetJourney()` query stay live in every environment, so this is a client-side visibility gate, not an API-level one; nothing stops a direct `POST /api/journey/reset` call elsewhere.

### 4.6 Ordering — ✅ Built (manual reordering removed; in-progress rows resurface to the top)
Rows in the **List** view were drag-reorderable per-account (`course_assignments.position`) — removed for producing bugs (a course could display in a different order than the roadmap intended, since a course with no manual position ever set fell back to `created_at`, which every course in a stage shares — they're all seeded in one statement). Nothing replaced the drag interaction as a *fetch-order* concern; instead `courses.roadmap_order` (migration 030), the catalog's own authored curriculum sequence, is the sole within-tier sort `getJourney()`/`getTrackWithCourses()`/`getCoursesForAutoSchedule()` (`features/learning/queries.js`) returns data in. `course_assignments.position` still exists as a column (nothing reads or writes it now) rather than being dropped. The Mind map view is a read-only display of whatever order the query returns, same as the List's own base order.

This is the fetch order only, not a required sequence — a learner isn't limited to working through `roadmap_order` top-to-bottom (4.10): any visible course can be started or have its quiz taken at any time, in any order. `JourneyTable` then applies one further, purely presentational re-sort on top of that base order: within each group (core, optional — 4.4), whatever's currently `in_progress` stably moves to the front, so an actively-worked-on course doesn't require scrolling past the rest of a tier to find. "Stably" means everything else keeps its relative order — this only pulls `in_progress` rows forward, and it never touches `courses.roadmap_order` itself (still what the Mind map and Auto Schedule read, unchanged).

### 4.7 Up next — ✅ Built (sidebar card)
Shows the next 2 courses that aren't complete/skipped: dated ones first (soonest `target_date`), then undated ones filling remaining slots in the roadmap's own order — a date is no longer required to appear here.

**No manual date-editing, no Refresh** — both removed on the product owner's own reasoning: this app was never really tracking *when* a learner studies (a course only genuinely moves once its wrap-up quiz is done — [03-your-journey.md](03-your-journey.md), 4.9), so a hand-picked `target_date` was a suggestion nothing downstream ever read back, while Auto Schedule already writes that same column for real. Refresh was redundant with `useRevalidateOnFocus`, which already re-fetches this whole page on tab-focus. Concretely:
- `POST /api/courses/:id/target` and its backing query (`setTargetDate()`) are gone from the codebase entirely, not just hidden — nothing calls them anymore.
- Each course row still *shows* its `target_date` read-only ("Target {date}" / "No target set") — only Auto Schedule writes it now.
- The moment a course becomes the #1 pick, it **automatically flips from `not_started` to `in_progress`** — a default "here's where to pick up," not a click. Never reverts real progress (a guard skips the write if the course is already anything other than `not_started`), and never pushes a track over its own in-progress cap either (4.10): if the track's already at `MAX_IN_PROGRESS_PER_TRACK`, this silently does nothing rather than starting a course nobody explicitly asked to start — no modal, since there's no click here to hang one off of. This pick is a suggestion, not the only way in: a learner can start (or jump straight to the quiz for) any other course directly from its own row (4.10), whether or not it agrees with this one.
- With nothing left to share header space with, **Auto Schedule is bigger and more visually prominent** than it used to be — a solid blue filled button with its own shadow, not the quiet light-accent pill it was one of two things next to before. Opens a modal asking for a position range — surfaced as a scrollable, checkable list of every not-yet-done course it covers, so a specific one can be left out of this run — and a **"Complete by" date** (not a number-of-months timeline anymore — see [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md), 8.5), then books real Google Calendar events for whichever courses stayed checked. Empty state when nothing qualifies: *"Nothing left to plan — every course is complete or skipped."*
- The button itself is **greyed out and disabled**, not just left to fail on click, until Google Calendar is actually connected (`calendarConnected`, from `getJourney()`) — a hover tooltip points at the hero's own Connect Google Calendar button (4.2) above. This is on top of, not instead of, the modal's own pre-existing inline "Connect Google Calendar" screen for a 409 `not_connected` response (a connection that dies between page load and the click) — that fallback is unchanged.
- A standing **amber banner inside the Up next card itself** (not just the button's hover tooltip) says the same thing more visibly whenever `!calendarConnected`: Auto Schedule can't book time or set target dates for you until Calendar's connected — there's no manual fallback to mention anymore, unlike before this pass.
- **"Remove from calendar"** — a single course's own undo, in the List view's row-expand (4.4), shown only when that course has a scheduled session: clears its calendar event(s) and target date, real course progress untouched (07-scheduler-auto-schedule.md, 8.5). There's no track-wide bulk version any more — a learner clears one course at a time.

### 4.8 Knowledge artifacts — ✅ Built (sidebar card, different shape than planned)
Re-scoped from "NotebookLM-generated mind map/summary/exam" ([06-planner-knowledge-builder.md](06-planner-knowledge-builder.md), still not started) to something real and much simpler: **the learner's own wrap-up quiz results.**

- The 3 most recently completed courses **in the selected track only** (4.3) — computed client-side from the same journey data the List view reads, re-deriving instantly when the track dropdown changes, no extra fetch — each showing `question count · time completed (relative) · first-try accuracy%` — e.g. "Claude 101 · 10 questions · 2 days ago · 90% accuracy." Sourced from `course_assignments.quiz_total_questions` / `quiz_correct_first_try`, a snapshot taken once at completion (4.9), not a live join — so a course whose quiz changes later still shows what was actually answered.
- A course completed before this existed (or with no stats sent) shows honestly as "No quiz data recorded" rather than a fabricated number.
- More rows below those: every `in_progress` course **in the selected track** (4.10 — up to `MAX_IN_PROGRESS_PER_TRACK`, so this can genuinely be more than one now, not just the single course Up next auto-picked), each labelled "In progress — waiting on the wrap-up quiz for more information," with a direct link to that course's quiz. Capped at 3 rows here regardless, mainly as a display ceiling rather than because more than that is expected.
- Empty state when nothing's complete and nothing's in progress **in the selected track**: "Complete a course's wrap-up quiz to see your results here."
- **Not surfaced elsewhere:** Team view's read-only drill-down into a learner's roadmap ([05-team-view.md](05-team-view.md)) doesn't show this card — an admin sees the roadmap table, not quiz stats, for someone else's account. It's also not shown on the Learner Dashboard's own "My courses" list — see [08-data-model.md](08-data-model.md)'s `course_assignments` entry for the current state of that gap.

### 4.9 Wrap-up — ✅ Built
Lives at `/learning/journey/[courseId]/quiz`. Linked from every row's own expanded detail again (4.4/4.10 — "Take the quiz"/"Retake the quiz"), not just Knowledge artifacts' (4.8) "in progress" nudge — a learner can jump into any course's quiz directly, whatever its current status, rather than only the single course this page happened to auto-pick as "in progress."

- One question per card, Trailhead/Salesforce-module style: click any option to check it against `course_quiz_questions.correct_answer`. Wrong just says "Incorrect — try another option" and stays clickable; right reveals the rationale and unlocks **Next question**. Every option stays clickable even after the right one's found — no locking, no attempt limit, matching how the quiz data itself was scoped (no attempts/answers table anywhere).
- Finishing the last question calls a real write: the course is marked `complete`, and how many questions were answered right on the *first* click (not any click after) is recorded as the accuracy snapshot 4.8 reads.
- A course with no quiz seeded (5 of the 20 — see [01-course-catalog.md](01-course-catalog.md), 2.1) shows "No quiz for this course yet" instead of a dead end.
- Already-completed courses can be retaken freely; retaking just re-writes the same snapshot.

### 4.10 Starting courses freely, and the in-progress cap — ✅ Built
The backend never enforced course order — `startCourse()`, `completeCourse()`, and `getCourseWithQuiz()` (`features/learning/queries.js`) have no prerequisite checks of any kind, and never did. Until this pass, the *UI* effectively imposed one anyway: the only way a course became `in_progress` was Up next's own auto-picked "next" course (4.7), and the only quiz link on the page pointed at whichever single course that was (4.8/4.9). Every other course in a tier was visible but functionally unreachable.

**Starting any course, in any order:** every row's expanded detail (4.4) now offers **"Start this course"** (hidden once a course is already `in_progress`/`complete`) and **"Take the quiz"/"Retake the quiz"** (shown regardless of status — `QuizPage.jsx` already handles "already complete — retake" and "no quiz yet" gracefully on its own). Clicking into the quiz for a `not_started` course starts it on the way in (subject to the cap below), so status still reflects what a learner actually did even when they jump straight to a quiz without a separate "Start" click first. Both actions are gated behind callback props (`onStartCourse`/`onSilentStart`) that only first-person views pass — this page, and the Learner Dashboard's "My courses" ([04-learner-dashboard.md](04-learner-dashboard.md)) — Team view's read-only drill-down ([05-team-view.md](05-team-view.md)) omits both, so an admin can't start or quiz a course on someone else's behalf.

**Up to `MAX_IN_PROGRESS_PER_TRACK` (2) courses in progress per track, no prompt:** starting a 1st or 2nd course in a track just starts it (`commitStartCourse`) — that range is the normal, expected case for a learner who likes working through a couple of things at once, not an edge case to warn about. The cap and the helper that checks it (`otherInProgressInSameTrack`, `MAX_IN_PROGRESS_PER_TRACK`, both `features/learning/shared.js`) are shared between this page and the Learner Dashboard since both render the same `JourneyTable`. Scoped per track, not per account — working through two different tracks in parallel isn't what this limits.

**Starting a 3rd means making room — `SwapStartModal`:** clicking "Start this course" when a track is already at the cap opens a small modal (`features/learning/SwapStartModal.jsx`, same visual family as `ConfirmModal` — shared `TONE` colors, same overlay/z-index) offering three choices, not a plain yes/no:
- Set aside one of the two current courses (back to `not_started`) and start the new one — 2 remain in progress.
- **"Just focus on"** the new course — sets *both* current courses aside and starts the new one alone — 1 remains in progress. This is what makes single-course-at-a-time and two-at-a-time equally real, supported outcomes, not just something the cap trends toward.
- Cancel ("Never mind") — nothing changes.

There's no "start a 3rd anyway" bypass — the cap is an actual ceiling, not a nag a learner can click past. Setting a course aside is a pure status flip back to `not_started` via a new, symmetric backend action — `unstartCourse()` (`features/learning/queries.js`) and `POST /api/courses/:id/unstart` — that only touches a row currently `in_progress` (never un-completes a finished course by mistake) and doesn't delete anything: any prior quiz snapshot on that course is untouched, and restarting it later works exactly like starting it the first time.

**The quiz link and Up next's own auto-pick never show this modal.** Both call a different function (`startIfNoConflict`) that just silently does nothing if starting would exceed the cap, leaving the course `not_started`. That's harmless for the quiz path specifically — `completeCourse()` doesn't care what a course's prior status was, so finishing the quiz still completes it normally either way, it just won't have shown as "in progress" in the interim. Interrupting either path with a modal was deliberately avoided: Up next's pick is a background effect with no click to anchor a modal to, and gating quiz access behind one would undercut "take any quiz, any time" for the sake of a rule that's really about deliberate starts, not quiz-taking.

**This is a client-side rule, not a server-side lock** — `startCourse()`/`completeCourse()` still accept any course, any time, same as before this pass, matching how the rest of this feature already trusts the client (no quiz attempt limits, no locking anywhere). Worth knowing if this ever needs enforcing harder later.

**Acceptance criteria (this page):**
- [x] A learner with zero enrolled tracks sees the empty state, never a broken roadmap
- [x] Skipped and not-started are visibly distinct from Complete/In progress
- [x] Knowledge artifacts show real quiz results for completed courses, plus a nudge for what's in progress
- [x] Wrap-up is a real quiz that marks a course complete, not a placeholder button
- [x] Up next reflects a real scheduled plan *(Auto Schedule writes real `target_date`s from real Google Calendar events — [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md))*
- [x] Any visible course can be started, or have its quiz taken, regardless of its position in the roadmap or its current status
- [x] A track can hold 1 or 2 courses in progress at once, by the learner's own choice — never silently more than that

The Mind map's own acceptance criteria live with the Mind map on the Learner Dashboard — see [04-learner-dashboard.md](04-learner-dashboard.md).
