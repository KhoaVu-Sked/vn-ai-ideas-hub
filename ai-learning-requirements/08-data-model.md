# Data model (Neon Postgres — what actually exists)

Part of [ai-learning-requirements](00-overview.md) — read that first for the status-tag legend and how these files relate.

All of these live in the same database as the rest of `vn-ai-ideas-hub`. Table design lives in `schema.sql` alone now — it's been split from content: the AI Track's actual courses and quiz questions are seeded separately, by `ai-track-seed.sql`, run once after `schema.sql` (same relationship as `seed.sql` to the Ideas Hub's own tables). `migrations/*.sql` are the additive deltas that got the schema here one step at a time; `schema.sql` always carries a full replay of all of them, so it's the one file to paste for either a fresh database or bringing an existing one current.

| Table | Purpose |
|---|---|
| `accounts` | Existing app-wide identity table (not learning-specific) — username, email, role, etc. Its `timezone` column (self-service, set on `/profile`) is what Auto Schedule reads to place study blocks at sensible local hours — [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md) |
| `user_role` | One seniority `position` per account: `intern` / `junior` / `middle` / `senior` / `principal`. Two writers now: a dropdown on Manage → Users (`features/admin/manage/UsersSection.jsx`, admin-only, unchanged), **and** the Get Started wizard's Role step (`POST /api/onboarding/position`, `setOwnPosition()` in `features/accounts/queries.js` — self-service, same upsert shape, no admin gate — [02-track-enrollment.md](02-track-enrollment.md)). Either writer drives the same things: tier-gating, the Mind map's columns, the profile-strip badge, and Auto Schedule's From/To defaults — [03-your-journey.md](03-your-journey.md), [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md) |
| `tracks` | Reference list of tracks (`AI Track`, `Core Competency`) |
| `account_tracks` | Many-to-many: which accounts are enrolled in which tracks — [02-track-enrollment.md](02-track-enrollment.md). Also what "onboarded" means for the Get Started gateway and the header nav (`exists(≥1 row)`, computed in `getProfile()` — deliberately NOT ANDed with `user_role.position` being set, since `user_role` predates this table by two migrations and an admin may never have set a position for an account that's genuinely already using the feature) |
| `courses` | The catalog — see [01-course-catalog.md](01-course-catalog.md), 2.1, for columns. Includes `skills` (`text[]`, migration 028) — a shared skill taxonomy feeding the Learner Dashboard's Retention card |
| `course_assignments` | One row per (account, course): `status` (`not_started`/`in_progress`/`complete`/`skipped`), `target_date` (the learner's own suggested date, set from Up next's pencil-edit **or** by Auto Schedule — a suggestion, not an enforced deadline), `position` (the learner's own drag-reorder within a tier), `quiz_total_questions` / `quiz_correct_first_try` (a one-time snapshot written when the course is marked complete — [03-your-journey.md](03-your-journey.md), 4.9), `calendar_event_id` (the Google Calendar event Auto Schedule created for this course, if any — migration 027, [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md)). `getJourney()` now returns all four of these on *every* course in the list, not just the 3 most recent completions — `calendar_event_id` + `updated_at` feed the Learner Dashboard's Weekly streak ([04-learner-dashboard.md](04-learner-dashboard.md)); the quiz-snapshot pair is present on every course too, but nothing currently renders a per-course score on the Dashboard's own "My courses" list (it reuses Your Journey's plain List columns, no score column) — today it's still only ever *displayed* via the separate, 3-row Knowledge artifacts path ([03-your-journey.md](03-your-journey.md), 4.8) |
| `course_quiz_questions` | The wrap-up quiz's actual content — see [01-course-catalog.md](01-course-catalog.md), 2.1 |
| `calendar_connections` | One row per account that's connected Google Calendar: an AES-256-GCM-encrypted refresh token (`lib/crypto.js`, `CALENDAR_TOKEN_KEY`) plus the scope actually granted — [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md) |
| `app_settings` | Existing app-wide key/value settings table (not learning-specific) — `key`/`value`/`updated_by`. This feature reads/writes one key, `annual_review_date` ([07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md), 8.6); `email_notifications` in the same table is the Ideas Hub's own, unrelated to learning |
| `ideas` | The Ideas Hub's own table (not learning-specific) — read here by `getMyIdeas()`/`getTeamIdeas()` (`features/learning/queries.js`) for the Learner Dashboard's and Team view's Application cards, `initiator_account_id`/`status` only. Not an idea↔course link — this feature still can't say which course or skill a given idea came from — [04-learner-dashboard.md](04-learner-dashboard.md), [05-team-view.md](05-team-view.md) |

**Not built, and not currently planned:** `courses_ref`, `assignments`, `progress`, `knowledge_artifacts` (the Knowledge artifacts *card* is real — [03-your-journey.md](03-your-journey.md), 4.8 — but it reads `course_assignments`' own snapshot columns, not a dedicated table), `reminders_log` (Auto Schedule books events but sends no reminders — [07-scheduler-auto-schedule.md](07-scheduler-auto-schedule.md)), `competency_uploads`, `skill_course_map`, `unmatched_skills` (these three were specifically the old self-serve upload-a-spreadsheet-and-fuzzy-match plan, [02-track-enrollment.md](02-track-enrollment.md) — not built, and superseded by the much simpler `courses.skills` tag array above for the one thing that plan would have fed, "confidence by skill"), `course_quiz_attempts`/`course_quiz_answers` (deliberately not built — no per-click or per-attempt history, just the one snapshot pair above), any `roadmap_status` column, and — despite the Learner Dashboard's "Progress by level" chart ([04-learner-dashboard.md](04-learner-dashboard.md)) — no `progress_level` column or table either: that chart's 4 levels are a pure client-side re-bucketing of `courses.expected_by_position`, computed in `features/learning/shared.js` and consumed only by `LearnerDashboardPage.jsx`; nothing in the schema, `queries.js`'s SQL, `MindMap.jsx`, `JourneyPage.jsx`, or `TeamPage.jsx` knows this grouping exists. If the upload/matching flow gets built later, expect new tables — don't assume these old names are what they'll be called.
